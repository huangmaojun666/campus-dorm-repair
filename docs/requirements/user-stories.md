# 校园宿舍报修系统用户故事清单

本清单对应软件工程课程设计第 2 次课检查点，共 25 条用户故事，其中功能需求 20 条、非功能需求 5 条。P0 为首版业务闭环及数据安全要求，P1 为补充能力与量化体验要求。

需求来源为 [已合并的调研报告](https://github.com/huangmaojun666/campus-dorm-repair/pull/3) 和 [项目 README](https://github.com/huangmaojun666/campus-dorm-repair/blob/main/README.md)。公共区域的重复报修还参考了宿管访谈纪要。

## 工单流程与试点口径

- 工单从待受理，经已受理、已转交、已安排、维修中和待验收，最终进入已关闭。待受理工单可以退回待补充，补充后重新受理。已关联是重复报修记录的状态，实际维修进度沿用主工单。
- 待验收时反馈未修好，原单进入待返修并开启新轮次，随后重新转交。已关闭后若故障复发，建立关联新单。公共区域主工单由主报修人验收，其他关联报修人可查共享进度。
- 首版拟由宿管联系总包并登记安排及变更，维修人员可使用试点账号接单，也可由宿管根据外部反馈代记。待验收满 48 小时标记超时，保留学生验收入口。涉及角色边界和超时处理的规则以团队评审与试点结果为准。
- 文件大小、通知时限和性能指标为拟定验收口径。GitHub 负责人按调研协作记录及模块拟分配，由团队评审确认。

## 功能需求

### US-01 账号登录与退出

**负责人** @huangmaojun666 · **优先级** P0

**用户故事** 作为学生、宿管或维修人员，我希望用已开通的账号登录和退出，以便在自己的工作入口办理报修或维修。

**需求来源** README「项目目标与角色」「技术栈」

**验收标准**

- **Given** 账号已启用且具有三个业务角色之一，**When** 使用正确凭据登录，**Then** 进入对应角色首页，页面刷新后仍保持当前登录状态。
- **Given** 凭据错误或账号停用，**When** 尝试登录，**Then** 显示无法登录的通用提示，且未建立登录会话。
- **Given** 用户已登录，**When** 退出后重新访问原工单页面，**Then** 系统要求重新登录，且不返回工单数据。

### US-02 提交房间或公共区域报修

**负责人** @dongzerich · **优先级** P0

**用户故事** 作为学生，我希望从统一入口提交故障位置和现象，以便宿管尽快定位并受理。

**需求来源** 调研报告 §7.1

**验收标准**

- **Given** 学生已登录，楼栋和对应房间或公共区域可报修，**When** 选择地点及故障类别并提交非空故障描述，**Then** 生成唯一工单号，工单状态为「待受理」，页面显示工单号及下一步提示。
- **Given** 报修表单缺少可定位的地点或故障描述，**When** 点击提交，**Then** 显示对应字段的错误，保留已填内容且不创建工单。
- **Given** 管理员已配置校方确认的紧急值班渠道，**When** 学生在报修入口查看紧急故障指引，**Then** 页面显示已配置的值班渠道和优先联系提示。

### US-03 添加故障照片

**负责人** @dongzerich · **优先级** P0

**用户故事** 作为学生，我希望给报修补充照片，以便宿管判断问题并减少来回询问。

**需求来源** 调研报告 §7.1，README「技术栈」。文件大小为拟定验收口径。

**验收标准**

- **Given** 学生正在填写报修表单且已有一张不超过 5 MiB 的 JPG 或 PNG 照片，**When** 上传并提交报修，**Then** 表单显示照片预览，提交后授权用户能在工单详情查看该照片。
- **Given** 选中的文件超过 5 MiB 或无法解码为受支持的图片，**When** 尝试上传，**Then** 界面提示大小或格式错误，已填字段和此前成功上传的照片仍可用。
- **Given** 学生已填完所有必填字段且没有添加照片，**When** 提交表单，**Then** 工单正常生成，附件区显示无附件。

### US-04 查看我的报修与进度

**负责人** @dongzerich · **优先级** P0

**用户故事** 作为学生，我希望在「我的报修」查看本人相关工单和下一步，以便知道报修是否已受理以及何时上门。

**需求来源** 调研报告 §6、§7.1–7.3

**验收标准**

- **Given** 学生名下有自行提交、宿管代录或已关联的工单，且系统中还有其他学生的无关工单，**When** 打开「我的报修」，**Then** 列表展示本人相关工单及编号、状态和更新时间，无关工单不出现在列表中。
- **Given** 学生打开一张已转交的工单，**When** 查看详情，**Then** 页面显示当前状态、负责角色、最近更新时间和下一步，且未定时段显示「待安排」。
- **Given** 宿管已登记预计上门时段及在场要求，**When** 学生重新查询该工单，**Then** 详情展示最新时段和是否需要在场。

### US-05 宿管代录群聊或线下报修

**负责人** @Scilana · **优先级** P0

**用户故事** 作为宿管，我希望代录群聊或线下收到的报修，以便这些报修也能有工单可查。

**需求来源** 调研报告 §7.1

**验收标准**

- **Given** 宿管负责目标楼栋且能识别报修学生，**When** 选择学生和来源，填写故障地点与描述并保存，**Then** 生成「待受理」工单，记录来源、代录人及时间，报修学生能在「我的报修」中查看。
- **Given** 宿管未选择可识别的报修学生或没有目标楼栋的管理权限，**When** 提交代录表单，**Then** 系统拒绝保存并说明原因，且不生成工单。

### US-06 审核报修与要求补充

**负责人** @Scilana · **优先级** P0

**用户故事** 作为宿管，我希望核对地点和故障现象并受理或要求补充，以便转交准确的报修信息。

**需求来源** 调研报告 §7.2

**验收标准**

- **Given** 所管楼栋的工单处于「待受理」且信息足够定位故障，**When** 宿管确认受理，**Then** 工单进入「已受理」，时间线记录处理人和时间，下一步为转交总包。
- **Given** 「待受理」工单的位置或故障现象需要澄清，**When** 宿管填写补充事项并提交，**Then** 工单进入「待补充」，报修人看到补充事项，系统生成通知记录。
- **Given** 工单已进入维修阶段或补充事项为空，**When** 宿管尝试要求补充，**Then** 系统拒绝本次变更并说明原因。

### US-07 补充报修信息并重新提交

**负责人** @dongzerich · **优先级** P0

**用户故事** 作为报修学生，我希望在原单补充宿管需要的信息，以便报修继续处理。

**需求来源** 调研报告 §7.2。补充后回到待受理为拟定流程。

**验收标准**

- **Given** 本人提交或由宿管代录的工单处于「待补充」，**When** 学生查看退回说明，补全所需信息后提交，**Then** 沿用原工单号，记录补充前后的信息和提交时间，工单回到「待受理」。
- **Given** 工单已由其他操作转为非「待补充」，**When** 学生从旧页面提交补充，**Then** 系统提示刷新查看最新状态，原处理记录保持完整。

### US-08 关联重复公共区域报修

**负责人** @Scilana · **优先级** P0

**用户故事** 作为宿管，我希望把同一公共设施的重复报修关联到主工单，以便只转交一次并让每位报修者都能查到进度。

**需求来源** 调研报告 §7.1，本地宿管访谈纪要「重复报修」

**验收标准**

- **Given** 两张未关闭的公共区域工单属于所管范围，且同一地点的故障经人工核对相同，待关联工单尚未转交，**When** 宿管选择主工单并确认关联，**Then** 保留双方报备记录，关联工单标记为「已关联」且失去独立转交入口，两位学生均可查询该故障的处理进度。
- **Given** 候选工单位于不同地点、是房间报修或已经转交，**When** 宿管尝试将候选工单作为重复记录关联，**Then** 系统拒绝关联并说明原因，两张工单各自保留原状态。
- **Given** 公共区域报修已经关联且另一位学生随后打开主工单的共享进度，**When** 学生查看时间线，**Then** 可看到状态、时间、上门时段和公开维修结果，其他报修人的姓名、联系方式和私有附件不展示。

### US-09 登记向总包转交

**负责人** @gloriousdream · **优先级** P0

**用户故事** 作为宿管，我希望在向总包转交后登记经手人和时间，以便确认故障已进入维修安排环节。

**需求来源** 调研报告 §7.2，本地宿管访谈纪要「进度查询」

**验收标准**

- **Given** 工单已受理或处于「待返修」，且当前处理轮次尚未登记转交，**When** 宿管填写接收方和实际转交时间并保存，**Then** 状态进入「已转交」，同时记录经手人、接收方、时间和所属轮次。
- **Given** 当前轮次已登记转交，或该工单为已关联的重复报修，**When** 宿管再次尝试登记转交，**Then** 系统提示已有转交或指向主工单，不新增转交记录。

### US-10 登记维修安排与预计上门时段

**负责人** @gloriousdream · **优先级** P0

**用户故事** 作为宿管，我希望记录总包反馈的维修安排，以便学生提前知道上门时间和是否需要在场。

**需求来源** 调研报告 §7.2，README「项目目标与角色」

**验收标准**

- **Given** 工单处于「已转交」且总包反馈了预计上门时段，**When** 宿管保存起止时间、在场要求及已有的人员安排，**Then** 工单进入「已安排」，学生可查看时段和在场要求，系统记录安排通知任务。
- **Given** 总包仅确认接手但尚未提供上门时段，**When** 宿管查看未安排的工单，**Then** 工单保持「已转交」且学生端显示「待安排」。
- **Given** 提交的结束时间早于或等于开始时间，**When** 宿管保存安排，**Then** 系统提示时段无效，并且不写入安排或通知。

### US-11 改派维修人员或调整上门时段

**负责人** @gloriousdream · **优先级** P0

**用户故事** 作为宿管，我希望协调改派和上门时段变更，以便无法按原安排维修时继续处理。

**需求来源** 调研报告 §7.2–7.3，README「项目目标与角色」。由宿管记录和确认变更为首版拟定方案。

**验收标准**

- **Given** 所管工单处于「已安排」或「维修中」，宿管获得了总包的变更反馈，**When** 填写变更原因并保存新人员或新时段，**Then** 时间线记录旧值、新值、经手人和时间，有新时段时通知相关报修人，改派后旧人员失去当前任务访问权。
- **Given** 改派发生在旧人员已开始处理之后，**When** 宿管完成改派，**Then** 保留旧人员的历史处理记录，新人员接手前工单回到「已安排」。
- **Given** 宿管没有填写原因或工单已进入「待验收」，**When** 尝试变更安排，**Then** 系统提示原因必填或状态不允许，原安排仍有效。

### US-12 查看并接手本人维修任务

**负责人** @gloriousdream · **优先级** P0

**用户故事** 作为有系统账号的维修人员，我希望查看和接手分配给我的工单，以便按安排处理故障。

**需求来源** 调研报告 §7.3，README「项目目标与角色」。维修人员账号用于首版试点，外部协调仍可由宿管代记。

**验收标准**

- **Given** 维修人员有当前分配给自己的「已安排」任务，**When** 打开任务列表并接手，**Then** 列表展示可处理任务及必要地点和故障信息，接手后工单进入「维修中」并记录时间。
- **Given** 任务已改派给其他维修人员，**When** 原维修人员尝试从旧列表接手，**Then** 系统拒绝，工单不会被原人员重新领取。

### US-13 记录维修进展与受阻原因

**负责人** @gloriousdream · **优先级** P0

**用户故事** 作为维修人员或代录宿管，我希望记录维修进度、受阻原因及下一步，以便宿管继续协调。

**需求来源** 调研报告 §7.2，README「项目目标与角色」

**验收标准**

- **Given** 在处理中的工单当前由该维修人员负责，或该工单在宿管代录范围且已有外部开工反馈，**When** 记录本次处理进展和下一步，**Then** 进展和记录时间进入当前轮次，外部开工代录可将「已安排」工单更新为「维修中」。
- **Given** 已安排或维修中的任务遇到入室受阻、缺配件或学生时段不便，**When** 授权人员登记原因与后续计划，**Then** 工单保留进行中的状态，学生端可查询对其公开的进展和下一步，宿管可查看完整协调记录。
- **Given** 提交受阻记录时缺少原因或下一步，**When** 尝试保存，**Then** 界面提示补齐字段，时间线不新增无效记录。

### US-14 登记维修结果并发起验收

**负责人** @uo10 · **优先级** P0

**用户故事** 作为维修人员或代录宿管，我希望登记本轮维修结果和可选照片，以便报修人确认故障是否处理完成。

**需求来源** 调研报告 §7.2–7.3

**验收标准**

- **Given** 工单处于「维修中」，当前维修人员或宿管已获得实际维修结果，**When** 填写处理结果并提交，可附照片，**Then** 结果归入当前轮次，工单进入「待验收」，学生能查看公开结果且系统生成验收通知任务。
- **Given** 处理结果为空或提交时工单已被改派且提交人失去权限，**When** 尝试提交，**Then** 系统拒绝提交并说明原因，且不生成验收通知任务。

### US-15 确认完工或稍后验收

**负责人** @uo10 · **优先级** P0

**用户故事** 作为主工单报修人，我希望查看结果后选择确认修好或稍后确认，以便核实后再关闭工单。

**需求来源** 调研报告 §7.3。公共区域关联学生可跟踪，主工单报修人处理统一验收，为拟定口径。

**验收标准**

- **Given** 当前轮次处于「待验收」且主工单报修人已核实故障修复，**When** 选择确认修好，**Then** 工单进入「已关闭」，记录确认人、时间和所属轮次。
- **Given** 工单处于「待验收」且报修人需要进一步观察，**When** 选择稍后确认，**Then** 界面返回工单详情或列表，工单继续待验收并可再次进入验收。
- **Given** 当前学生只是关联报修人，或同轮已被处理，**When** 尝试提交验收，**Then** 系统不受理该动作，既有验收及工单状态保持一致。

### US-16 申请返修与关联复发报修

**负责人** @uo10 · **优先级** P0

**用户故事** 作为报修学生，我希望故障未修好或结单后复发时继续报修，以便宿管查到过去的处理结果。

**需求来源** 调研报告 §7.3，本地宿管访谈纪要「完工与返修」

**验收标准**

- **Given** 主工单处于「待验收」，且报修人仍发现相同故障，**When** 填写原因并提交未修好反馈，**Then** 沿用原工单号，进入「待返修」，新增返修轮次并保留前一轮转交、维修结果及失败原因。
- **Given** 本人原工单已关闭，且相同故障再次发生，**When** 从原工单发起关联报修并提交，**Then** 生成新的「待受理」工单并保存原工单号，原工单保持已关闭。
- **Given** 报修人未填写未修好的原因，**When** 提交返修，**Then** 系统提示补充原因，当前工单仍待验收且不产生返修轮次。

### US-17 提交维修评价

**需求来源** README「项目目标与角色」，调研报告高校报修系统对比。评分范围为拟定口径。

**验收标准**

- **Given** 本人确认完工的工单已关闭且尚无评价，**When** 选择 1–5 星并提交可选意见，**Then** 保存一份评价，学生和授权宿管可查看该评分和提交时间。
- **Given** 工单尚未确认关闭、已有评价或评分超出 1–5 星，**When** 尝试提交评价，**Then** 系统拒绝并提示原因，不产生无效或重复评价。

### US-18 发送报修关键进度邮件

**负责人** @uo10 · **优先级** P0

**用户故事** 作为学生，我希望在需要行动或安排有变时收到通知，以便补充信息、安排在场或确认维修结果。

**需求来源** 调研报告 §7.2，README「技术栈」。邮件延迟和去重边界为拟定验收口径。

**验收标准**

- **Given** 报修人有有效邮箱且第三方邮件服务可用，**When** 工单要求补充信息、确定或更改上门时段、或进入待验收，**Then** 系统保存通知记录并在 1 分钟内收到邮件服务的接收确认，邮件包含工单号、事件和登录后查看入口。
- **Given** 邮件服务暂时不可用，**When** 工单发生需要通知的状态变化，**Then** 新工单状态正常可查，系统记录发送失败并保留可重试的通知任务。
- **Given** 同一通知事件已获服务接收确认，**When** 重放该通知任务，**Then** 系统不再次发起发送请求，已发送记录仍可追踪。

### US-19 跟进楼栋积压与超时验收

**负责人** @Scilana · **优先级** P1

**用户故事** 作为宿管，我希望按楼栋和状态筛选待处理工单并查看超时验收，以便优先跟进长时间无反馈的记录。

**需求来源** README「项目目标与角色」，调研报告 §7.3。试点拟采用 48 小时提醒，工单保留待验收状态。

**验收标准**

- **Given** 所管楼栋已有不同状态的工单，包含进入待验收满 48 小时的工单及尚未满 48 小时的工单，**When** 宿管打开工作台、按楼栋和状态筛选并启用超时条件，**Then** 只列出该管理范围内到达阈值的待验收工单，筛选结果总数与相同条件的详情列表一致。
- **Given** 工单到达 48 小时阈值且学生无回应，**When** 重新加载工作台，**Then** 工单显示超时标记并继续处于「待验收」，学生仍能选择确认或反馈未修好。

**负责人** @Scilana · **优先级** P1

**用户故事** 作为宿管，我希望维护所管楼栋的房间和公共区域，以便报修准确定位并能回看历史地址。

**需求来源** README「项目目标与角色」，调研报告 §7.1

**验收标准**

- **Given** 目标楼栋在宿管管理范围内，位置编号在同一楼栋的同类位置中未被使用，**When** 宿管新增房间或公共区域并启用，**Then** 该位置出现在对应楼栋的新报修地点选项中。
- **Given** 某个位置已有历史工单，**When** 宿管停用该位置，**Then** 新报修表单不再允许选择该位置，历史工单仍显示登记时的位置。
- **Given** 地点编号重复或楼栋超出管理范围，**When** 宿管提交位置新增或编辑，**Then** 系统拒绝保存，并保留原位置数据。

## 非功能需求

### NFR-01 工单和附件的访问控制

**负责人** @huangmaojun666 · **优先级** P0

**用户故事** 作为报修学生和宿管，我希望工单数据和附件仅对授权人员开放，以便保护宿舍和联系方式等信息。

**需求来源** 调研报告 §7.3，README「登录与权限」

**验收标准**

- **Given** 访客未登录，**When** 请求受保护的工单或附件接口，**Then** 接口返回 HTTP 401，响应中不包含受保护数据。
- **Given** 已登录用户请求他人的私有工单、未分配给本人的维修任务或所管楼栋之外的工单与附件，**When** 直接读取资源或提交状态操作，**Then** 接口返回 HTTP 403 或 404，且不返回该资源内容或写入变更。
- **Given** 学生是公共设施主工单的关联报修人，或维修人员是当前分配对象，**When** 访问相应工单，**Then** 接口仅返回该角色可见的字段，关联学生看不到其他报修人的身份与私有附件，维修人员只获得执行任务所需信息。

### NFR-02 工单查询响应性能

**负责人** @huangmaojun666 · **优先级** P1

**用户故事** 作为需要跟进工单的学生和宿管，我希望列表和详情在常见负载下快速响应，以便及时查到最新处理进度。

**需求来源** 调研报告 §6「进度」场景。下述数据量和性能指标为拟定验收口径。

**验收标准**

- **Given** 应用与数据库运行在同一台 4 vCPU、8 GiB 的测试主机，预置 10,000 张工单，列表分页大小为 20，**When** 预热 1 分钟后，用 30 个已登录的并发虚拟用户按 1∶1 比例混合请求列表首页和工单详情，持续 5 分钟，**Then** 从压测端记录，两类接口各自的响应时间 P95 均不超过 2 秒，且各自的请求失败率低于 1%。
- **Given** 数据及压测参数与前一场景一致，**When** 完成一次压测，**Then** 报告可分别核对列表和详情的请求数、P95、失败率以及实际测试环境。

### NFR-03 工单提交幂等与状态一致性

**负责人** @huangmaojun666 · **优先级** P0

**用户故事** 作为提交和处理工单的用户，我希望重试和并发操作都有一致结果，以便避免重复工单或覆盖他人的处理。

**需求来源** 调研报告 §7.1、§7.3

**验收标准**

- **Given** 同一学生的一次提交已经入库，但客户端未收到响应，**When** 使用该次提交的标识重试同一报修信息，**Then** 系统返回原工单号，数据库中只有一张对应工单及一条初始状态记录。
- **Given** 一张待验收工单同时收到确认修好和反馈未修好两个基于同一版本的有效请求，**When** 服务端并发处理请求，**Then** 只有一个请求改变状态，另一请求收到状态已变化的提示，工单、处理轮次及时间线与成功请求一致。

### NFR-05 关键操作审计与历史保留

**负责人** @huangmaojun666 · **优先级** P0

**用户故事** 作为宿管，我希望关键状态和分派变更均可追溯，以便处理争议和复盘。

**需求来源** README「项目目标与角色」，调研报告 §7.2–7.3

**验收标准**

- **Given** 测试工单依次经历受理、转交、安排、改派、完工、返修和关闭，**When** 授权宿管查看审计记录，**Then** 每次成功变更都有工单号、轮次、操作人、时间、前后状态，改派额外有前后维修人员和原因。
- **Given** 工单经过改派和返修，且较早记录中已有维修结果，**When** 查询原轮次的审计记录，**Then** 早期记录及对应处理结果仍可按时间查看，普通业务角色无法通过工单操作修改这些历史记录。
